# Tmux handoff

Prepare an isolated task worktree and a self-contained handoff, open the worktree with `tnc`, and start interactive `puss` in build mode with the originating session's current model profile in its empty shell pane. Keep the user's current window and pane focused throughout creation and launch. Do not implement the handed-off task in the originating session.

## Prepare

1. Read the project's safety instructions and load the `gwt` skill. Every handoff, including read-only tasks, must run in a dedicated task worktree, never the main checkout or an unrelated task's workspace. Reuse a worktree only when it was explicitly designated for this task; otherwise create one with `gwt create <base-ref> <task-name>` and capture its returned path. Use the requested base ref, or resolve the repository's default branch rather than assuming `origin/main`. Check the source checkout for uncommitted changes. If the task needs them, ask how to carry them over; never silently omit, move, stash, or discard them. Verify the resulting branch and working directory. If creation fails or the sandbox mount excludes sibling worktrees, stop and report the blocker. Never fall back to the current checkout or raw worktree commands.
2. Carry approved changes before launching. For a move, apply a path-scoped patch in the task worktree, verify it matches the source changes, then reverse only that patch in the source checkout. Do not use a blanket restore or stash. Check both working trees afterward. Copy any required untracked files separately. Copy useful scratch scripts and results into the shared handoff directory; `/tmp` files and installed tools in the originating sandbox will not survive into the receiver. Remove hardcoded scratch paths or document the exact setup needed to rerun them.
3. Write a uniquely named handoff under the project's `julsemaan-tmp/` using `write_tmp_document`. Include the goal, decisions, relevant files, implementation steps, validation commands, safety restrictions, and known blockers. State that workspace setup and window creation are already handled so the receiver does not repeat the handoff. Include any uncommitted changes the receiver must preserve. Do not include credentials or the entire conversation.
4. Confirm the handoff is readable through the task worktree and both paths are visible on the host and inside the `puss` mount. `gwt` may symlink `julsemaan-tmp` from the main checkout; verify its target is mounted too. Record the task worktree path and branch in the handoff, and instruct the receiver to work only there. Do not assume sandbox paths exist on the host.

## Preserve the current model profile

Before launching, capture the originating session's effective profile and all three model aliases with their thinking levels. Read only the relevant `build-plan-mode` state from the current session identified by `PI_SESSION_FILE`, or use the extension's current-profile output. Resolve missing state from the extension's runtime state or profile override using its actual precedence rules. An empty `PI_BUILD_PLAN_MODEL_PROFILE` does not mean the default is active, and a concrete `PI_MODEL` does not identify the whole profile. If the effective profile cannot be determined, ask rather than guess.

For a built-in profile, launch `puss --model-profile <captured-profile>`. For a custom profile, launch `puss` without a task, then restore the captured mappings through `/large-model <provider/model> <thinking>`, `/medium-model <provider/model> <thinking>`, and `/small-model <provider/model> <thinking>` in the receiving session. Never replace custom mappings with a built-in profile or change a shared `julsemaan-tmp/model-profile` file to configure one handoff. Record the captured configuration in the handoff.

## Use the host helpers

Read the current definitions before launching. The source is `~/src/profile/`:

- `profile/bashrc.d/10-tmux.bash`: `tnc` aliases `tmux-new-coding` and accepts `--background <directory>`, not a command. Worktree windows are named after their branch.
- `tmuxifiers/coding.window.sh`: the coding layout starts Neovim and devbox panes and leaves an empty shell pane. Inspect the layout rather than hardcoding pane numbers.
- `profile/bashrc.d/30-ai.bash`: `puss` launches sandboxed Pi with `~/src` mounted.

`tnc`, `tmuxifier`, and `puss` may be absent from the agent container. This is expected. Sourcing profile files or running `bash -lic` inside the container does not grant host execution.

Run every tmux CLI call as `letee tmux <args>`, never bare `tmux`. This includes read-only queries, `run-shell`, `send-keys`, and pane capture. Never use `select-window`, `select-pane`, or `switch-client` for a handoff, even followed by a switch back. `letee tmux` passes arguments unchanged, so keep the explicit `-S <socket>` and `-t <target>` on every call. If `letee tmux -V` fails, stop and report it rather than falling back to bare `tmux`.

Before invoking helpers, check whether repository restrictions also prohibit bare tmux calls inside `tnc` or tmuxifier. If so, ask for a narrow handoff-only exception. Without that exception, stop and provide manual instructions. Permission to create a window does not permit restarting or reconfiguring a server.

Both helpers are host shell aliases. Invoke a host `bash -lic` through the existing tmux server's `letee tmux -S <socket> run-shell -t <source-pane>`. First run a read-only host preflight that checks `type tnc`, `type puss`, and `command -v tmuxifier`. Check each result, for example `rc=0; type tnc || rc=1; type puss || rc=1; command -v tmuxifier || rc=1; exit "$rc"`. A successful last command alone is not sufficient. Also check host access to the task worktree and handoff. Proceed only if every check passes. If the socket or host helpers are unavailable, stop and provide manual host instructions. Do not install or recreate the helpers inside the container.

### Capture host output without touching Pi's display

Host `run-shell` output can overwrite the originating Pi display. For both preflight and window creation, allocate separate, uniquely named `.log`, `.status`, and `.done` paths under the shared `julsemaan-tmp/`. Verify the directory is writable and readable through both host and sandbox paths before running helpers. If shared logging is unavailable, stop; never fall back to pane output.

Host interactive startup can emit OSC title sequences containing expanded shell commands and credentials. Never save or display raw `bash -lic` startup output, run `env`/`set`, or enable shell tracing. Filter the entire host invocation's combined output, including startup output, before it reaches any file or tool response. Strip terminal control sequences and retain only explicit, anchored handoff result markers. Emit those markers after startup, with success/failure codes for each preflight check and window creation, and the final empty-shell pane ID. Do not include environment values in markers. Obtain only relevant sanitized diagnostics on failure. If raw output was accidentally persisted, remove that log without printing or copying it into the handoff.

In the enclosing host shell, save the host invocation's exit status immediately, independently of the output filter's status. Write the numeric host status to `.status`, then create `.done` only after the status write and filtered log both complete successfully. Suppress outer redirection-failure diagnostics so they cannot reach the source pane. Capture the `letee tmux` invocation's own stdout/stderr in a separate sanitized local invocation log. Shell-quote every path and payload at each shell boundary, including paths containing spaces. Do not redirect the later interactive `puss` session.

Host and sandbox `/tmp` are different filesystems. Treat a missing sandbox log as a path-visibility problem, not evidence that the host command failed. Never repeat a state-changing call just to recover its log.

Wait for `.done`, then use filesystem tools to read `.status`, the filtered `.log`, and the sanitized invocation log. The tmux command returning successfully is not completion of the host operation. Use a bounded completion wait, such as 30 seconds; a missing marker, unreadable status, nonzero status, or invocation failure is a blocker. Report captured errors without replaying logs through tmux. Never retry window creation solely because completion is uncertain.

Use shell-quoted arguments. Do not substitute bare `pi`, print mode, or redirected Pi stdin/stdout. The receiving session must remain interactive.

## Launch

1. Discover the current tmux socket and session from the actual environment. Resolve stable session/window/pane IDs with read-only queries. Never hardcode a username, UID, socket, or session ID from another task. Use an explicit socket and session/pane targets for every `letee tmux` command.
2. After the logged host preflight completes successfully, run `tnc --background <absolute-task-worktree-path>` through the same logged host execution route. Never invoke `tnc` directly with the agent's bash tool inside the container. Background `tnc` picks its session from `TMUX_PANE`, and `run-shell` jobs inherit whatever `TMUX_PANE` the server's global environment holds, which can point at another session. The `run-shell -t` target does not override it. Start the host payload with `export TMUX_PANE=<source-pane-id>;` so the window lands in the source pane's session.
3. Record existing window IDs server-wide with `list-windows -a` before creation and identify the new window by the ID difference after the creation marker and successful status arrive. Do not identify it by name alone, as names can collide. Confirm the new window's `#{session_id}` equals the source pane's session ID. If creation is ambiguous, fails, or lands in another session, stop, report the actual session and window IDs, and inspect the captured logs rather than creating another window. Record the new window's stable pane IDs and inspect the layout. Reject the originating pane as a launch target.
4. Poll the new window's panes once per second for up to 30 seconds using `letee tmux -S <socket> list-panes -t <new-window-id> -F '#{pane_id} #{pane_current_path}'`. Split each row only at the first space so directory paths containing spaces remain intact. Require a nonempty pane list with the recorded IDs and every pane directory equal to the absolute task worktree path before launching Pi. Compare canonical host paths if symlinks are involved. Do not treat an initial mismatch as failure or assume asynchronous startup is the cause. On timeout, report each pane ID and its actual directory together with captured host errors. Stop without recreating the window, sending corrective `cd` commands, or weakening the all-pane check.
5. Identify the empty shell pane without selecting it. Background creation logs its stable pane ID as the final layout output; cross-check that ID against the new window's recorded pane IDs and layout. Inspect `pane_current_command` and `capture-pane -p -t <new-shell-pane-id>` through `letee tmux -S <socket>` to verify an idle shell before sending anything. Never send commands to the originating agent, Neovim, a running devbox startup, or an existing user process.
6. Target every `send-keys` and `capture-pane` call explicitly at `<new-shell-pane-id>` with `letee tmux -S <socket>`. Never rely on the active pane or window. In that background shell, launch `puss --model-profile <captured-profile>` for a built-in profile, or `puss` for a custom profile. Shell-quote arguments. Do not pass the handoff as an initial prompt: new sessions default to plan mode. The shell must have loaded the aliases. Prefer sending the launch command to the new interactive shell rather than replacing its shell process, so launch errors remain visible. Do not pipe the prompt into Pi.
7. Wait for Pi's input editor. Restore custom mappings if needed, then submit `/build` and wait for confirmation. Submit `/model-profile` and verify all alias models and thinking levels match the captured configuration. Verify the status shows build mode. Do not use `PI_SUBAGENT=1` as a mode workaround or invent a `--build` flag. If configuration differs or a command fails, stop before sending the task.
8. Only after mode and profile verification, submit a normal Pi prompt telling the receiver to read and execute the handoff at its absolute path in the task worktree. Treat the path as prompt text, not a shell command. Check the pane output to confirm the handoff was read. A successful window-creation exit code is not evidence that Pi launched. If startup is still underway, report that instead of claiming completion. If it exits, capture the actual error from the pane before retrying. Do not repeat a launch merely because the original window did not visibly change.

## Safety and completion

- Respect repository tmux restrictions unless the user explicitly grants a narrow handoff-only exception. Otherwise, provide manual instructions when restrictions prevent using `tnc`. Do not restart, kill, or reconfigure servers, modify shell configuration, install tools, or bypass sandbox restrictions to make the handoff work.
- If host execution or helper access is unavailable, save the handoff and provide a shell-quoted host command using `tnc --background` and interactive `puss` without focus-changing commands. Report the exact blocker and any captured error. Do not invent an error when none was captured.
- Do not run a live handoff merely to test this skill. Validate commands with stubs or inspect definitions unless the user requests a launch.
- Finish with the workspace, branch, new window/pane IDs, handoff path, verified build mode, inherited profile, and launch status. Leave the user's original focus untouched. Report the target IDs so the user can switch when ready. Do not wait for the receiver to complete the implementation unless asked.
